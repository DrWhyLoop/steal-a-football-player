# Game overview
"Steal a Footballer" â€” a Roblox steal-and-collect game (like Steal a Brainrot / Steal an Egg) with original cartoon football-legend characters.

Core loop:
- Players mine collectible egg meshes with a pickaxe in a 12-stage hallway (Stage 1 nearest the bases, 192 studs wide; stages 1-8 are about 442.86 studs long, stages 9-10 are 553.57, stage 11 is 664.29 and stage 12 is 885.71; total stage pathway 6,200 studs).
- A broken egg drops a character card of that stage's tier; the player carries it back (slower for higher tiers) and places it on one of 30 raised displays across three floors of their plot. Placed characters earn cash per second.
- Tiers: Stages 1-2 Common, 3-4 Rare, 5-7 Epic, 8-9 Legendary, 10-11 Mythic, 12 GOAT. GOAT cubes only spawn as a timed Stage 12 event. A random Golden Cube (stages 4-11) drops one tier higher, capped at Mythic.
- 6 plots per server, max 6 players.

Built so far: 6,200-stud running pathway with extended green ground and walls; 14 reference-textured player models linked to server-weighted egg rewards, plus the separate preview lineup; full-map grassy terrain and nearby client-generated landscaping, perimeter collision/grass-top borders, 120 dim nighttime torches, synchronized sunny/rain/evening/night weather; greybox world, six tiered egg designs using the cube mining system, ground-floor plot fences, cards, carrying, plots with 180 working gray displays, green earnings panels, separate yellow upgrade panels, cash, Golden Cube; pickaxe mining/combat with hit/miss sounds and server line-of-sight checks; stealing with original-owner validation, reserved slots marked BEING STOLEN, and recovery on pickaxe/guard hits; base lock with a 60s barrier, 30s cooldown and both countdowns; 28 imported-monster stage guards with patrol/chase, nearby-player activation, distance-limited effects and client knockback.

Receipt-test flake root cause (2026-11-05): the intermittent Phase 4 receipt-check failure was in the TEST, not in Purchases. The failure injection ("fail the Nth RequestSave") counted every PlayerData.RequestSave call, so a background save (autosave, a grant's save, a strike clear) landing while a receipt save was waiting for its coalesce window shifted the count and the failure hit the wrong call. Reproduced with background saves running and a 1.5s save window: the old all-saves counting failed 20/20 iterations (a background save counted as the receipt's own: 3 saves counted instead of 2); counting only saves made by the receipt's own coroutine (everything else passes straight through) passed 20/20 under identical conditions. Purchases and every other source file were not changed (all hashes unchanged); the test was a temporary bridge script and was removed.
Separate finding from ruling Purchases out (NOT fixed, awaiting the user's decision): two simultaneous deliveries of the SAME receipt ID can double-grant. In a probe both calls returned PurchaseGranted and cash rose by 200 instead of 100: the second call sees the receipt already pending (created by the first call, which is still waiting for its save) and proceeds to grant. Proposed fix: an in-flight set keyed by receipt ID so a concurrent duplicate returns NotProcessedYet (Roblox retries and then sees Done). Config.Purchases.Products is empty, so no product can be bought today and nothing is currently exposed.

Receipt atomicity and in-flight guard (2026-11-05; supersedes the pending-then-grant ProcessReceipt described in the Phase 4 entry and the double-grant finding above):
- Found and fixed a real flaw in PlayerData.RequestSave: a caller that changed data after an in-flight save's snapshot joined that save and got `true` although its change was not in it (measured: change to 99 after a snapshot of 7, RequestSave returned true at 0.67s with persisted cash still 7). It now uses a per-request job: once the scheduled save starts, p.job is cleared and the next request schedules a new one, so a returned `true` always means a save whose snapshot came AFTER the call. Coalescing is unchanged (3 simultaneous requests = 1 immediate save; 3 right after a save = 1 save at the 6s window; verified live). This also hardens the Phase 0 steal-transfer ordering.
- Receipts (Purchases.ProcessReceipt): single-save pattern. The cash grant and the receipt ID ({At}) change together in memory with no yield, ONE RequestSave persists both, and PurchaseGranted is returned only after it succeeded (failure returns NotProcessedYet; the in-memory grant stays, so Roblox's retry is recognised as a duplicate, saved, and granted without regranting). Receipts no longer have a Done/pending state (the schema is {At}; no product exists so no data was ever written). A receiptsInFlight[PurchaseId] guard refuses a concurrent duplicate with NotProcessedYet; the body runs in a pcall so the guard is always released and an error returns NotProcessedYet.
- Crash walk-through (modelled with a deep-copying, slow persisted store and a re-send of the receipt to a profile loaded from what was persisted): crash before the grant, before the save, or inside the save before the write -> nothing persisted (receipt and cash both absent), the re-sent receipt is granted once (cash 100); crash after the save returned but before PurchaseGranted -> receipt and cash persisted together, the re-sent receipt is recognised and returns PurchaseGranted without granting (cash 100). The persisted receipt/cash pair was consistent at every crash point. The old pending-then-grant flow also survived every crash point (it only stays safe through its two-save ordering) but failed the RequestSave contract and the two-at-once case (both calls returned PurchaseGranted, live and persisted cash 200).
- Results: harness on the OLD code 2 FAIL (RequestSave contract, two-at-once); on the NEW code 11/11 pass (the two old-flow-only crash points cannot trigger any more because there is a single save); live modules: 20 iterations with background saves running, 2-at-once (exactly one PurchaseGranted, cash +100), coalescing checks 4/4, and the real tap path (Premium -> granted + equipped).
